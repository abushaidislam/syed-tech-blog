প্রতিটি ক্রমবর্ধমান স্টার্টআপ একসময় একই ভীতিকর আর্কিটেকচারাল মাইলফলকের মুখোমুখি হয়: একটি মাল্টি-টেরাবাইট প্রোডাকশন ডেটাবেস, যেখানে হাজার হাজার সক্রিয় কানেকশন রয়েছে। সেখানে একটি সাধারণ `ALTER TABLE ADD COLUMN` চালানো বা কোনো ফরেন কি (foreign key) রিনেম করা পুরো রিলেশনকে লক করে দিতে পারে, অ্যাপ্লিকেশন কানেকশন পুলকে নিঃশেষ করে দিতে পারে এবং একটি বড় ধরনের গ্লোবাল বিভ্রাট ঘটাতে পারে।

ছোট বা প্রাথমিক পর্যায়ের অ্যাপ্লিকেশনে মেইনটেন্যান্স উইন্ডো মেনে নেওয়া যায়। আপনি রবিবারের রাত ২টায় একটি ঘোষণা দিয়ে মেইনটেন্যান্স স্ক্রিন চালু করে মাইগ্রেশন স্ক্রিপ্ট চালাতে পারেন এবং প্রার্থনা করতে পারেন যেন রোলব্যাক করার প্রয়োজন না হয়।

কিন্তু এন্টারপ্রাইজ স্কেলে, মেইনটেন্যান্স উইন্ডো এমন একটি বিলাসিতা যা কোনো হাই-অ্যাভেইল্যাবিলিটি ব্যবসার পক্ষে বহন করা সম্ভব নয়। গ্লোবাল ইউজার বেস ২৪ ঘণ্টা সব টাইম জোনে সক্রিয় থাকে। এই আর্কিটেকচারাল গাইডে, আমরা জিরো-ডাউনটাইম স্কিমা পরিবর্তনের পরীক্ষিত ইঞ্জিনিয়ারিং ব্লুপ্রিন্ট বিশ্লেষণ করব: **এক্সপ্যান্ড-কন্ট্রাক্ট প্যাটার্ন**, **অ্যাসিঙ্ক্রোনাস ঘোস্ট টেবিল** এবং **রিয়েল-টাইম চেঞ্জ ডেটা ক্যাপচার (CDC)**।

## ৫-ধাপের জিরো-ডাউনটাইম মাইগ্রেশন লাইফসাইকেল

বড় টেবিলগুলোকে এক্সক্লুসিভ লক দিয়ে ইন-প্লেস পরিবর্তন করার পরিবর্তে, এন্টারপ্রাইজ সিস্টেমগুলো প্রতিটি স্ট্রাকচারাল মিউটেশনকে পাঁচটি আলাদা ধাপে বিভক্ত করে:

<Steps>
  <Step title="ধাপ ১: নন-ডেস্ট্রাক্টিভভাবে স্কিমা এক্সপ্যান্ড করা" badge="Additive DDL">
    শুধুমাত্র অ্যাডিশনাল পরিবর্তনগুলো ডেপ্লয় করুন। নতুন কলামগুলো অবশ্যই `NULLABLE` হিসেবে যোগ করতে হবে, যাতে ব্যয়বহুল টেবিল-লকিং ডিফল্ট ভ্যালুর প্রয়োজন না হয়। এই ধাপে বিদ্যমান কোনো কলাম রিনেম বা ড্রপ করবেন না।
  </Step>

  <Step title="ধাপ ২: অ্যাপ্লিকেশন লেয়ারে ডুয়াল-রাইটিং" badge="Dual Writes">
    আপনার অ্যাপ্লিকেশন সার্ভিস লেয়ারকে আপডেট করুন যাতে সেটি একই ট্রানজ্যাকশনের ভেতরে অথবা অ্যাসিঙ্ক্রোনাস চেঞ্জ ডেটা ক্যাপচার (CDC) ওয়ার্কারের মাধ্যমে পুরনো এবং নতুন উভয় কলাম/টেবিলে ডেটা লিখতে পারে।
  </Step>

  <Step title="ধাপ ৩: ব্যাচে ঐতিহাসিক রেকর্ড ব্যাকফিল করা" badge="Async Backfill">
    একটি ব্যাকগ্রাউন্ড ওয়ার্কার প্রসেস চালান যা ছোট, ডিটারমিনিস্টিক প্রাইমারি কি ব্যাচে (যেমন প্রতিবার ১,০০০ সারি) ঐতিহাসিক রেকর্ডগুলো আপডেট করবে। ডেটাবেস I/O স্যাচুরেশন এড়াতে এতে অ্যাডাপ্টিভ থ্রটলিং ব্যবহার করুন।
  </Step>

  <Step title="ধাপ ৪: শ্যাডো রিড এবং কন্টিনিউয়াস ভেরিফিকেশন" badge="Shadow Mode">
    শ্যাডো মোডে নতুন স্কিমা থেকে রিড করা শুরু করুন। অ্যাপ্লিকেশন উভয় রিপ্রেজেন্টেশন থেকেই রিড করবে, সেমান্টিক সমতা যাচাই করবে, অসামঞ্জস্যতা দেখা দিলে টেলিমেট্রি ইমিট করবে এবং কোনো অমিল থাকলে পুরনো ফরম্যাটকেই ডিফল্ট হিসেবে ব্যবহার করবে।
  </Step>

  <Step title="ধাপ ৫: লিগ্যাসি কলাম কন্ট্রাক্ট এবং ক্লিনআপ করা" badge="Schema Contraction">
    একবার টেলিমেট্রি নিশ্চিত করলে যে ডেটা ১০০% সামঞ্জস্যপূর্ণ এবং সমস্ত সার্ভিস শুধুমাত্র নতুন স্কিমা থেকেই রিড করছে, তখন একটি চূড়ান্ত কন্ট্রাকশন মাইগ্রেশন চালিয়ে লিগ্যাসি ফিল্ড এবং রিডানড্যান্ট ট্রিগারগুলো ড্রপ করে দিন।
  </Step>
</Steps>

<Callout type="tip">
**আর্কিটেকচার টিপ:** PostgreSQL-এর ১১-এর চেয়ে পুরনো ভার্সনে কয়েক কোটি সারি থাকা টেবিলে কখনোই `DEFAULT 'some_string'` ব্যবহার করবেন না। আধুনিক ইঞ্জিনগুলোতে নন-ভোলাটাইল ডিফল্টসহ কলাম যোগ করা একটি মেটাডেটা-অনলি অপারেশন, তবে ফরেন কি কনস্ট্রেইন্ট এবং ইনডেক্স যোগ করার জন্য এখনো `CONCURRENTLY` ব্যবহার করা প্রয়োজন।

## মাল্টি-ল্যাঙ্গুয়েজ ইমপ্লিমেন্টেশন: ডুয়াল-রাইটিং রিপোজিটরি

আধুনিক প্রোডাকশন ব্যাকএন্ডে বিভিন্ন স্ট্যাকে কীভাবে নিরাপদ ডুয়াল-রাইটিং ইমপ্লিমেন্ট করা হয় তা নিচে দেওয়া হলো:

<CodeTabs items={["TypeScript (Prisma)", "Go (pgx)", "SQL (Postgres)"]}>
  <Tab label="TypeScript (Prisma)">
```typescript
// src/repositories/orders_repository.ts
export async function createOrderDualWrite(data: CreateOrderInput) {
  return await prisma.$transaction(async (tx) => {
    // 1. Write to legacy schema representation
    const legacyOrder = await tx.order.create({
      data: {
        userId: data.userId,
        totalCents: data.amountCents,
        status: data.status,
      },
    });

    // 2. Dual-write to new partitioned representation
    await tx.orderPartitioned.create({
      data: {
        orderId: legacyOrder.id,
        userUuid: data.userUuid,
        amountDecimal: data.amountCents / 100,
        state: mapStatusToEnum(data.status),
        createdAt: legacyOrder.createdAt,
      },
    });

    return legacyOrder;
  });
}
```
  </Tab>

  <Tab label="Go (pgx)">
```go
// pkg/repository/order.go
func (r *OrderRepository) CreateOrderDualWrite(ctx context.Context, o *Order) error {
    tx, err := r.pool.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)

    // 1. Write to legacy table
    queryLegacy := `INSERT INTO orders (user_id, total_cents, status) VALUES ($1, $2, $3) RETURNING id`
    var orderID int64
    if err := tx.QueryRow(ctx, queryLegacy, o.UserID, o.TotalCents, o.Status).Scan(&orderID); err != nil {
        return err
    }

    // 2. Dual write to modernized target table
    queryNew := `INSERT INTO orders_v2 (order_id, user_uuid, amount_decimal, state) VALUES ($1, $2, $3, $4)`
    if _, err := tx.Exec(ctx, queryNew, orderID, o.UserUUID, float64(o.TotalCents)/100.0, o.State); err != nil {
        return err
    }

    return tx.Commit(ctx)
}
```
  </Tab>

  <Tab label="SQL (Postgres)">
```sql
-- Safe, non-blocking index creation on multi-million row table
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_v2_user_uuid_state
ON orders_v2 (user_uuid, state)
WHERE state IN ('PENDING', 'PROCESSING');

-- Verification query for shadow parity checks
SELECT 
    COUNT(*) AS mismatch_count
FROM orders o
LEFT JOIN orders_v2 v2 ON o.id = v2.order_id
WHERE v2.order_id IS NULL 
   OR o.total_cents != CAST(v2.amount_decimal * 100 AS BIGINT);
```

## বিস্তারিত আলোচনা: ঘোস্ট টেবিল বনাম অনলাইন স্কিমা চেঞ্জ

৫০০ মিলিয়নের বেশি সারি থাকা টেবিলের ক্ষেত্রে, `CREATE INDEX CONCURRENTLY` ও CPU স্পাইক এবং ভ্যাকুয়াম স্টারভেশন ঘটাতে পারে। হাই-স্কেল প্রযুক্তি কোম্পানিগুলো **ঘোস্ট টেবিল টুলস** (যেমন GitHub-এর `gh-ost` বা MySQL-এর `pt-online-schema-change`) এর ওপর নির্ভর করে:

```
Client Ingestion ──> [ Original Table ] ──(Binlog / CDC Stream)──> [ Ghost Table (_orders_gho) ]
                             │                                             ▲
                             │                                             │
                             └────────── Background Backfill ──────────────┘
```

১. **ঘোস্ট টেবিল তৈরি:** কাঙ্ক্ষিত পরিবর্তনগুলো প্রয়োগ করে একটি ডুপ্লিকেট স্কিমা টেবিল `_orders_gho` তৈরি করা হয়।
২. **স্ট্রিম বিনলগ মিউটেশন:** একটি লাইটওয়েট ডেমন ডেটাবেস রেপ্লিকেশন স্ট্রিম থেকে সারির পরিবর্তনগুলো ক্যাপচার করে এবং অ্যাসিঙ্ক্রোনাসভাবে ঘোস্ট টেবিলে রেপ্লিকেট করে।
৩. **অ্যাটমিক সোয়াপ:** ব্যাকফিল ৯৯.৯৯৯% সম্পন্ন হলে, ইঞ্জিন ১০ মিলিসেকেন্ডের কম সময়ে একটি অ্যাটমিক টেবিল রিনেম (`RENAME TABLE orders TO orders_old, _orders_gho TO orders`) সম্পন্ন করে।
